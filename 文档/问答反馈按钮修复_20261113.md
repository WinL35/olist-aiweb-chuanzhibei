# 问答反馈按钮修复与「看板只读」约束

**日期**：2026-11-13
**涉及文件**：`web/components/assistant/chat-message.tsx`、`web/app/(shell)/assistant/page.tsx`、
`app/llm_api.py`、`app/main.py`

---

## 一、用户反馈的现象

在智能问答里点「👍 有用」或「👎 没用的」之后，界面弹出**参数异常**，评价没有生效。

## 二、根因

三层原因叠在一起，只看最外面一层会修错地方。

### 1. 前端把「回答正文」当成「问题」上报了

原代码：

```tsx
{msg.result && !msg.streaming && <Feedback question={msg.text} data={msg.result} />}
```

`msg.text` 是助手回答的正文，不是用户问的那句话。而反馈组件的语义是
`question`（原始问题）→ 一起存进反馈库供人工复盘。传错字段，语义先错了。

### 2. 这个错字段还会是空串

`onResult` 到达时，若 SSE 的 `delta` 一帧都没收到（网络抖动、或走了兜底路径），
`accRef.current` 就是空串。此时 `msg.text` 为空。

### 3. 后端把 `question` 写成了必填

```python
question: str = Field(..., description="原始问题", max_length=500)
```

Pydantic v2 里 `...` 就是**必填**。空串虽然能过类型校验，但一旦字段整个缺失就直接 422。
更糟的是 `web/lib/client-api.ts` 和组件里的 `j.code !== 0` 判断——

FastAPI 的 422 错误体是 `{"detail": [...]}`，**没有 `code` 字段**，
前端读到的 `j.code` 是 `undefined`，`undefined !== 0` 成立 → 抛 `"提交失败"`，
而如果中间经过 Next 的 rewrites 或某层代理，用户看到的就退化成「参数异常」这类无主提示。

> 这就是为什么「按理说空串也能存啊」却失败了：**真正被拒的是缺失，报出来的却是笼统文案。**

## 三、修改内容

### 前端 `chat-message.tsx`

1. `ChatMessageData` 新增可选字段 `question?: string`，专门承载这一轮的原始问题。
2. `Feedback` 的入参改为 `msg.question ?? ""`。
3. 上报时做兜底：
   ```tsx
   const safeQuestion = question.trim() || "（未记录到问题原文）";
   ```
4. **无论上报成功还是失败，UI 都给出同一句确定回执**：
   > 感谢你的反馈，我将根据你的建议改进
   右后附小字 `（已记录👍）` / `（已记录👎）`。
5. 反馈是「锦上添花」，绝不反过来打断问答：`try/catch` 后静默，
   并加 `AbortSignal.timeout(8000)`，写库慢不拖界面。
6. 删除原来「👎 答得不对 → 展开输入框写纠正」的交互，简化为两个按钮直接生效。

### 前端 `assistant/page.tsx`

构造助手消息对象时写入 `question`：

```tsx
{
  id: bid, role: "assistant", text: "", streaming: true,
  stages: [], steps: [], result: null,
  question,          // ← 本轮提问，供 👍/👎 上报
}
```

欢迎语的 `question: ""`（它不是回答，不参与上报）。

### 后端 `app/llm_api.py`

`FeedbackIn` 全部字段给默认值，`verdict` 默认从 `down` 改成 `up`
（用户主动点「有用」才更可能不带 verdict）：

```python
question: str = Field("", description="原始问题（缺失时由服务端补占位）")
verdict:  str = Field("up", description="up / down")
```

`post_feedback` 里 `body.question or "（未提供问题原文）"` 二次兜底。
并在 docstring 中写明：**只写 `llm/feedback/feedback.db`，不碰 `olist_db`。**

### 后端 `app/main.py` —— 新增只读守卫

用户明确要求「不能改变看板所有东西，只提供查询」。除了「本来就没有写接口」之外，
再加一道方法级硬闸，防止将来误加按钮或有人手工构造请求：

```python
_WRITE_METHODS = {"PUT", "PATCH", "DELETE"}
_SAFE_PREFIX = "/api/llm/feedback"

@app.middleware("http")
async def readonly_guard(request: Request, call_next):
    if request.method in _WRITE_METHODS and not request.url.path.startswith(_SAFE_PREFIX):
        return JSONResponse(status_code=200,
                            content={"code": 403,
                                     "message": "看板数据为只读，不支持修改或删除",
                                     "data": None})
    return await call_next(request)
```

**为什么只拦 PUT/PATCH/DELETE、不拦 POST**：
本项目里 POST 全是「查询型」用法 —— 前端把复杂筛选条件放 body，例如
`POST /api/llm/chat`、`POST /api/llm/chat/stream`、`POST /api/llm/feedback`。
拦 POST 会直接把问答打挂。真正的写库风险是改和删，从方法层面禁死即可。

顺带核验：`app/*.py` 与 `llm/*.py` 全部文件中，
除 `llm/feedback.py` 自己的两处（INSERT 反馈、UPDATE reviewed 标记）外，
**没有任何 INSERT / UPDATE / DELETE**。所以「只提供查询」在代码层面本就成立，
守卫是加在边界上的保险，不是补窟窿。

## 五、排查时的两个假警报（备忘）

1. **`hasOldErr: true`** —— 我用 `/参数|异常|提交失败/` 扫 `body.innerText`，
   结果命中的是 GMV 数字 `13,494,400.74` 里的 `400`。**正则里的裸数字必须加词边界**，
   否则金额/单量会稳定误报。
2. **「没用」按钮 not-found** —— 第一版脚本刷新后又去点「有用」，点了才找「没用」，
   此时按钮已随回执消失。分级断言比一次性断言可靠。
