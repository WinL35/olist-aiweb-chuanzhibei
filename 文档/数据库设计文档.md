## 一、总体结构

本项目使用**两个数据库**，均在同一 MySQL 实例（`localhost:3306`）上：

| 库名 | 用途 | 表数 | 总行数 | 与谁相关 |
|---|---|---|---|---|
| `olist_db` | 主业务库：原始数据清洗后的宽表 | 13 | 872,359 | 后端2 的经营看板、转化分析 |
| `olist_algo_db` | 算法结果库：算法1/算法2 的产出 | 9 | 96,462 | 后端2 的分群、预测、选品、定价接口 |

**合计 22 张表，968,838 行数据。**

### 1.1 为什么分成两个库

1. **职责隔离**：`olist_db` 由原始数据生成（可重复清洗重建），
   `olist_algo_db` 由算法产出（模型迭代时只需重导后者），互不干扰。
2. **重建安全**：清洗脚本 `pipeline/load_mysql.py` 会 `DROP TABLE` 主库的 13 张表，
   若算法结果同库，会被连带清空。
3. **跨库查询零成本**：两库在同一实例，SQL 里写全限定名即可
   （`SELECT * FROM olist_algo_db.algo1_rfm_user_tags`），
   **后端只需要维护一个数据库连接**。

### 1.2 后端连接方式

```python
# backend/config.py
DB_CONFIG = {
    "host": "localhost", "port": 3306, "user": "root",
    "password": "123456",              # 或用环境变量 MYSQL_PASSWORD
    "database": "olist_db",            # 主库
    "charset": "utf8mb4",
}
ALGO_DB = "olist_algo_db"              # 跨库查询时作为表名前缀
```

```python
# 跨库查询示例（只连 olist_db）
SELECT rfm_segment, COUNT(*)
FROM olist_algo_db.algo1_rfm_user_tags
GROUP BY rfm_segment;
```

**关联键说明：**

| 关系 | 关联键 | 基数 |
|---|---|---|
| `fact_sales` → `dim_product` | `product_id` | N : 1 |
| `fact_sales` → `dim_seller` | `seller_id` | N : 1 |
| `fact_sales` → `dim_customer` | `customer_id` | N : 1 |
| `fact_sales` → `fact_order` | `order_id` | N : 1 |
| `fact_order` → `fact_order_master` | `order_id` | 1 : 1 |
| `fact_order` → `fact_review` | `order_id` | 1 : 1 |
| `fact_order` → `fact_order_payment_agg` | `order_id` | 1 : 1 |
| `fact_order_master` → `dim_customer` | `customer_id` | N : 1 |
| `fact_rfm` → `dim_customer` | `customer_unique_id` | 1 : 1 |

> **注意**：`customer_id`（订单级客户标识）与 `customer_unique_id`（真实用户）
> 是**两个不同的键**。一个真实用户可以有多个 `customer_id`。
> RFM 与用户分群必须用 `customer_unique_id`，否则会严重高估用户数。

### 2.2 算法库 `olist_algo_db` 的关系

```
                ┌──────────────────────────┐
                │ algo1_rfm_user_tags      │
                │ customer_unique_id (PK)  │  95,420 行
                │ K-Means 4 类 + 规则 8 类  │
                └────────────┬─────────────┘
                             │ 可按 customer_unique_id
                             │ 与主库 fact_rfm / dim_customer JOIN
                             ▼
┌─────────────────────────┐         ┌──────────────────────────┐
│ algo2_selection_result  │◄────────│ algo2_pricing_result     │
│ (selection_type, rank)  │ 按 product_id 关联（1:1）           │
│ product_id              │         │ product_id (PK)          │
└────────────┬────────────┘         └────────────┬─────────────┘
             │                                    │
             │ 与 algo2_pricing_skipped           │
             │ 互补（有建议价 vs 无建议价）        │
             ▼                                    ▼
┌──────────────────┐  ┌────────────────────┐  ┌──────────────────────┐
│ algo2_forecast_  │  │ algo2_offline_     │  │ algo2_selection_     │
│ result           │  │ experiment         │  │ hitrate              │
│ (category, week) │  │ (cat, model, hold) │  │ (level, strategy)    │
└──────────────────┘  └────────────────────┘  └──────────────────────┘
     598 行                 296 行                   4 行

统一由 algo_import_log 记录每次导入
```

**跨库 JOIN 示例**（后端做综合分析时用）：

```sql
-- 主库的 4 类 K-Means 分群 与 算法库的 8 类规则分群 对照
SELECT f.rfm_segment AS 后端4类,
       a.rfm_segment_rule8 AS 算法8类,
       COUNT(*) AS 用户数
FROM olist_db.fact_rfm f
JOIN olist_algo_db.algo1_rfm_user_tags a
  ON f.customer_unique_id = a.customer_unique_id
GROUP BY f.rfm_segment, a.rfm_segment_rule8
ORDER BY 用户数 DESC;
```

3. **幂等可控**：脚本用「先清空、再插入」的事务，反复执行结果一致。

## 七、数据一致性校验

每次入库脚本都会自动执行校验，结果写入 `algo_import_log`。

### 7.1 算法1 的校验项（9 项）

| 校验项 | 通过标准 |
|---|---|
| 行数一致 | CSV 行数 == 数据库行数（95,420） |
| 用户ID唯一 | 无重复主键 |
| 核心字段非空 | R/F/M/分群标签 无 NULL |
| **F 分与购买次数一致** | F≥3 必须对应 frequency≥3（防五分位失真） |
| rfm_score 拼接正确 | `rfm_score == r||f||m` |
| 得分范围 | R/F/M 均在 1~5 |
| K-Means 簇数 | 恰为 4 |
| 规则分群类别数 | 恰为 8 |
| 抽样核对 | CSV 前 3 行与库内一致 |

### 7.2 算法2 的校验项（28 项）

- 7 张表各自的**行数一致**、**关键字段非空**
- 4 张表的**抽样核对**
- 跨表业务校验：选品商品数 == 定价商品数、定价商品都能在选品表找到、
  无建议价商品集合 == 定价跳过表、汇总统计数字与实际 COUNT 一致、
  每品类均有 4 个模型记录、导入日志无失败

### 7.3 已知的数据一致性问题（重要）

| 问题 | 现状 | 处理 |
|---|---|---|
| **两套 RFM 分群并存** | `fact_rfm` 有 4 类 K-Means，`algo1_rfm_user_tags` 有 4 类 K-Means + 8 类规则 | 建议后端统一用算法库的 8 类，前端图例同步改 |
| **v1 版 F 分失真** | 旧脚本用五分位，把 54,339 个只买 1 次的用户标成"高 F" | **已修正**为业务阈值法（v2），`f_score_quantile` 列保留旧值供对比 |
| `review_score` 100% 非空 | 宽表中评价分被填满，不能判"是否已评价" | 漏斗改用 `review_creation_date` |

## 九、设计取舍与局限

### 9.1 为什么用宽表而不是严格范式

`fact_order_master`（33 列）和 `fact_sales`（27 列）是**反范式设计**，
把客户、支付、评价、物流属性直接冗余进事实表。

**理由**：后端的看板接口需要在一次查询里拿到多表字段，
如果严格按 3NF 拆表，每个接口都要 4~6 个 JOIN，
在 10 万行规模上响应时间会从 100ms 涨到 600ms+。
宽表用存储空间换查询速度，是 OLAP 场景的标准做法。

### 9.2 为什么保留 `fact_order` 与 `fact_order_master` 两份

- `fact_order`：只含订单核心字段（8 列），用于轻量查询；
- `fact_order_master`：全字段宽表（33 列），用于看板聚合。

冗余但各有用途，查询时按需选择。

### 9.3 局限

1. **无分区表**：`fact_sales` 11 万行尚不需要，但数据量到千万级应加时间分区。
2. **无外键约束**：导入时设 `FOREIGN_KEY_CHECKS=0` 加速，
   但表之间**没有实际的 FK 约束**，数据完整性靠脚本校验保证。
   若需强约束，可后续补 `ALTER TABLE ... ADD CONSTRAINT`。
3. **视图层已建立，但后端未全部切换**：主库已有 **10 个视图**（见 9.4），
   但 FastAPI 查询仍主要直查事实表。原因是视图采用"有效订单口径"
   （`v_order_sales_detail` 基于订单商品明细，剔除了取消/不可用订单），
   与看板现有口径相差约 0.2%，直接切换会导致全站数字漂移，
   故本次先做视图沉淀，供 BI / Navicat / 后续改造使用。
4. **口径统一建议**：后续若切换视图，需同步更新算法侧统计与文档基准数字，
   避免"看板 13,591,644 / 视图 13,56x,xxx"两套数并存。

## 9.4 视图层（10 个）

建库脚本：`Olist_Views.sql`（全部建在 `olist_db`，需 MySQL 8.0+）。

| 视图 | 用途 |
|---|---|
| `v_order_sales_detail` | 订单商品明细宽表（类型清洗 + 运费分摊 + 净收入），其余视图的基础 |
