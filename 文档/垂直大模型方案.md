# 面向中小电商的垂直行业大模型方案

> 参赛：兴智杯全国人工智能创新应用大赛 · 垂直行业大模型赛道
> 团队：卢泳豪（大数据 2403）　｜　版本：v1.0　｜　2026-10-29
>
> 一句话：**在已有的 Olist 经营分析平台上，把 22 个真实数据接口、32 条行业口径
> 硬规则、239 段行业文档，组装成一个"懂行、能算、敢拒答"的经营决策助手。**

---

## 一、赛题理解：为什么"通用底座 + 行业数据"还不够

赛题要求"融合通用模型与行业数据，让模型懂行业、能做精准决策、形成可迁移方法论"。
我们对这句话的理解是三个递进的门槛：

| 门槛 | 通用大模型的做法 | 问题 | 我们的做法 |
|---|---|---|---|
| **懂行** | 用公开百科知识回答 | 电商口径与常识冲突（GMV≠营收） | 口径库写进 system prompt，优先级高于先验 |
| **能算** | 凭训练记忆给数字 | 数字是编的，不可核对 | 22 个工具实时取数，数字只有一个来源 |
| **敢拒** | 顺着问就一定给答案 | 给不出也说"大约" | 边界写死成代码，宁可承认不知道 |

**这三点恰好是"垂直"两个字的全部含义**：不是把模型换个行业名字，
而是把**行业口径、行业数据、行业边界**三样东西变成模型不可绕过的约束。

---

## 二、为什么选电商经营决策这个行业

三个理由，按重要性排序：

1. **痛点真实且高频**。中小电商每天要回答的问题高度重复：这个品类要不要备货？
   哪些商品该降价？我的模型准不准？——而老板通常没有数据分析师。
2. **"懂行"的门槛是可验证的**。GMV 是不是营收、客单价是不是人均消费、
   转化率是浏览转化还是支付转化——这些问题的对错可以**当场二元判定**，
   不像"文案好坏"那样说不清。这让评测成为可能。
3. **我们有真实的数据底座**。已在 Olist 巴西电商数据集上建成
   13 张业务表 + 10 个视图（872,359 行）、9 张算法结果表、33 个 GET 接口、
   7 个可视化页面、2 套算法。大模型层不是空中楼阁，是**长在已有系统上的一层**。

> 这一点很关键：很多参赛方案的"行业数据"是临时爬的几百条；
> 我们的每一条数字都能在 MySQL 里查到行，也能在网页上点出来。

## 四、知识层：把"口径"变成模型的硬约束

### 4.1 硬规则：33 条，只写"会答错的地方"

不是把教科书搬进去，而是**只收团队真实踩过的坑**。每条结构：

```json
{"id": "GMV-01",
 "topic": "GMV 定义",
 "keywords": ["gmv", "营收", "营业额"],
 "wrong": "GMV 就是营收。",
 "correct": "GMV 是商品金额，不含运费、不扣成本，不等于营收也不等于用户实付。",
 "evidence": "全量 13,591,643.70；实付 16,008,872.12；运费 2,251,909.54",
 "source": "文档/口径手册.md"}
```

覆盖 8 个主题：金额规模（4）、用户订单（5）、数据质量（5）、
预测（5）、选品（4）、定价（6）、系统合规（3）。

**设计要点：硬规则与软知识分离。**

- `always=True` 的 23 条（如"GMV 不含运费"）**无条件注入** system prompt——
  它们错了整段回答就废了；
- 其余 10 条按关键词匹配后注入，避免 prompt 过长；
- 文档片段（RAG）**只作依据引用，不作数字来源**——数字必须来自工具。

### 4.2 RAG：为什么选 TF-IDF 而不是向量库

| 方案 | 优点 | 为什么没选 |
|---|---|---|
| 向量检索（bge/m3e） | 语义泛化好 | 要下载模型（400MB+），现场断网就废；答辩机器不一定有 GPU |
| BM25（rank_bm25） | 轻量 | 需额外依赖，且中文分词质量不稳定 |
| **TF-IDF char_wb 2-4gram** | **零依赖、离线可用、可解释** | 语义泛化弱（同义词换说法可能捞不到） |

选择理由很实际：**赛题要的是能跑起来的系统，不是跑分最高的组件**。
char_wb 2-4gram 对中文无需分词，239 段语料的检索延迟 <20ms。

> 已知不足：语义泛化弱。检索不到时会显式输出"本次未检索到相关片段"，
> 而不是假装有依据——这一点比召回率更重要。

## 五、工具层：让模型"能算"，而不是"会编"

### 5.1 22 个工具怎么来的

把现有 33 个 GET 接口中与经营决策最相关的 22 个翻译成 function calling schema。
**关键设计：db 模式直接调用 `app/` 里的路由函数**，不是重写 SQL——
所以模型报的数和网页上看到的数**一模一样**，不存在"两个真相"。

```
模型说 → tools/executor.py → app/dashboard.py::summary() → MySQL
                              ↑ 与前端页面同一条代码路径
```

CSV 降级：MySQL 不可用时自动读 `cleaned/*.csv`，返回里带 `source: csv-fallback`
标识，前端和回答里都会显示数据源。

### 5.2 工具描述是"调度指令"，不是注释

每条 description 都写清"什么时候**必须**调"：

> `dashboard_summary`：凡是问「整体规模/大盘怎么样」**必须先调这个，禁止凭印象给数字**。

这一句的作用超过十倍 prompt 工程——它把"该不该调工具"的判断从模型自由裁量
变成了明确规则。

## 六、决策层：Agent 的双路径

### 6.1 LLM 路径（有 API Key）

标准 ReAct 循环，最多 4 步、6 次工具调用：

```
问题 → 护栏检查 → 检索 → [模型思考 → 调工具 → 观察结果]×N → 最终回答
```

工具结果以 JSON 回填，模型基于真实数字组织语言。
若 4 步内没收敛，**自动降级到离线组装器**，保证不空手返回。

### 6.2 离线路径（无 Key / 断网）

确定性规则引擎：意图识别 → 调同一批工具 → 按模板组装。
三个用途：

1. 现场断网也能演示完整链路（评委常见要求）；
2. 作为评测**下界**——规则引擎能答对的，说明知识层有效；
3. 与 LLM 路径共享工具与规则，评测可公平对比。

### 6.3 输出结构固定

强制四段式，每句话都能被追问：

```
【结论】一两句说清，带关键数字
数据依据  逐条「指标：数值（来源工具）」
口径提醒  本次依赖的行业口径（带规则编号）
局限      这次结论不能用于什么场景
```

## 七、安全：三重护栏，全部写死在代码里

赛题强调"安全可信"。我们的原则：**护栏不靠 prompt，靠代码**。
prompt 可以被诱导，`if` 不能。

| 护栏 | 实现 | 例子 |
|---|---|---|
| **① 越界拒答** | `guard.py` 11 条正则 | 问"卖家 A 明天卖多少"→ 直接拒，给替代方案 |
| **② 口径篡改拦截** | `composer.policy_overrides()` 7 条 | "把取消订单算进 GMV 让数字好看"→ 结论第一条就纠正 |
| **③ 调价幅度约束** | `check_price_bound()` + 模型层 ±15% 夹取 | "提价 50%"→ 说明约束，不给该幅度的数 |

第②条是我们认为最有价值的设计。用户说"把复购率改成 10% 好看点"时，
模型**无权答应**——规则命中后强制在结论开头输出"不能，实际 3.05%"。

> 这类"改口径"请求在企业内部极其常见，也是数据造假的主要入口。
> 用代码拦，比用 prompt 劝，可靠得多。

## 八、微调策略：为什么现在不做 LoRA，以及什么时候做

**诚实说明：当前版本没有做参数微调。** 理由：

1. 微调解决的是"格式/风格/领域语言"，解决不了"数字真实"——后者必须靠工具；
2. 33 条口径规则 + prompt 已能达到 100%（开发集），微调的边际收益不明；
3. 没有 GPU 资源，强行微调只能做小模型，反而降低推理质量。

**但方案里保留微调路径**，触发条件明确：

| 触发条件 | 微调目标 | 数据构造 |
|---|---|---|
| 接入真实企业数据后，口径规则 >100 条 | 把口径内化为参数，省 prompt | 规则 → (问题, 正确回答) 对 |
| 需要固定话术风格（如给老板看的周报） | 风格对齐 | 人工撰写 200 条周报样例 |
| 有 GPU 且需要离线部署 | 小模型蒸馏 | 用大模型跑 5,000 条问答做教师 |

数据构造方式：用现有 `questions.jsonl` 的 60 题做种子，让强模型生成
同义改写（每题 10 种问法），再用我们的**规则引擎打分过滤**——
只有答对的样本进入训练集。这样能避免"把错误答案学进去"。

## 九、评测：四类题 × 四种模式

### 9.1 设计

| 类别 | 考什么 | 题数 | 判定方式 |
|---|---|---|---|
| A 口径陷阱 | 会不会被常识带偏 | 15 | 必须出现正确口径 + 关键数字 |
| B 多步决策 | 会不会真的去取数 | 15 | 必须出现工具返回的真实数值 |
| C 拒答 | 知不知道自己不知道 | 15 | 必须拒答 + 给替代方案 |
| D 边界/合规 | 会不会被诱导违规 | 15 | 必须拒绝篡改 + 说明依据 |

评分完全基于字符串匹配（`must_any` 事实组 + `must_not` 禁忌表述），
**不含任何人工判断**，任何人可复现。

消融实验四模式：`baseline`（裸底座）→ `no_tools`（只有知识）→
`no_rag`（知识+工具）→ `full`。

### 9.2 结果

| 模式 | A 口径 | B 多步 | C 拒答 | D 边界 | 总体 | 工具命中 | 依据覆盖 |
|---|---|---|---|---|---|---|---|
| baseline | 0% | 0% | 0% | 0% | **0.0%** | 0% | 0% |
| no_tools | 93.3% | 53.3% | 100% | 86.7% | **83.3%** | 0% | 90% |
| no_rag | 100% | 100% | 100% | 100% | **100%** | 97.1% | 0% |
| full | 100% | 100% | 100% | 100% | **100%** | 97.1% | 90% |

**三个必须讲清的读法：**

1. **baseline 0% 不是"通用模型很笨"**，而是演示一个事实：没有工具和口径的
   通用模型，在垂直问题上会给出"看起来对、实际错"的答案（GMV=营收）。
   这正是赛题要解决的"通用可用 vs 垂直好用"的差距。
2. **B 类从 53.3% → 100% 是工具层的贡献**——不加工具，模型根本拿不到 518.3 件、
   90.46%、31 个建议价这些数。
3. **RAG 的准确率增量是 0，但依据覆盖率从 0% → 90%**。
   诚实结论：在当前评分体系下，检索不改变对错（事实来自工具与硬规则），
   它提供的是**可核对性**。RAG 的真实价值需要接入真模型后测语言组织质量才能体现。

### 9.3 盲测：100% 不可信，75% 才是

主评测集是"边写题边补规则"的，100% 说明规则库覆盖了这 60 题，**不代表泛化**。
所以另写 20 道问法不同的盲测题，写完只跑一次：

| 题目集 | 题数 | 总体 |
|---|---|---|
| 主评测集（开发集） | 60 | 100%（会过拟合） |
| **盲测集 第一次** | 20 | **75%** |

**5 道失败全部是"意图路由没覆盖问法"，不是知识错**——同一问题换个说法
（"被剔掉的那 549 行"而不是"取消订单"）就路由不到对应工具。

这个发现比 100% 更有价值：它说明**规则式路由是当前架构的真实瓶颈**，
也解释了为什么必须接入真模型做语义路由。补完 5 条正则后重测 100%，
但那个数已经不能算盲测，对外只报 75%。

## 十、可迁移方法论：换一个行业怎么复制

这是我们希望被记住的部分——**方法比结果更可迁移**。

### 五步法

| 步骤 | 动作 | 判据 |
|---|---|---|
| **1. 考古** | 翻遍历史代码、报表、会议纪要，收集所有"曾经答错"的问题 | 收集到 ≥30 个真实错误 |
| **2. 定口径** | 每个错误写成「错误说法 → 正确口径 → 数据依据」三元组 | 每条都能用 SQL 复核 |
| **3. 建工具** | 把已有 API/SQL 翻译成 function calling，**复用原代码** | 模型数 = 网页数 |
| **4. 立边界** | 明确列出"做不到"清单，写成正则或代码 | 越界请求 100% 被拦 |
| **5. 双集评测** | 开发集迭代 + 盲测集只跑一次 | 两个数都报 |

### 跨行业可直接套用的部分

- **架构**：知识（硬规则+检索）→ 工具 → Agent → 评测，五层不动；
- **硬规则格式**：`{id, topic, keywords, wrong, correct, evidence, source}` 通用；
- **评测协议**：`must_any` + `must_not` + 四模式消融，与行业无关；
- **口径拦截器**：任何行业都有"想改数字让报表好看"的诉求，正则库可换行业重写。

### 需要重写的部分

| 组件 | 换行业时 |
|---|---|
| 33 条口径规则 | 全部重写（这是行业知识的实体） |
| 22 个工具 | 换成本行业的数据接口 |
| 越界正则 | 换成本行业的"做不到"清单 |
| RAG 语料 | 换成本行业文档 |

## 十二、已知不足（主动列出）

1. **规则式路由不鲁棒**：盲测暴露的 5 处失败全是路由问题，靠补正则治标不治本；
2. **RAG 语义泛化弱**：TF-IDF 对同义改写召回差，换成向量检索需解决离线部署；
3. **未做参数微调**：口径靠 prompt 注入，规则变多后 prompt 会膨胀；
4. **评测集规模小**：80 题覆盖有限，且由作者自写，存在主观偏差；
5. **离线模式的诚实性**：报告里所有离线数字都标注了"仅反映管线有效性"，
   不能当作大模型能力指标——这一点我们不会包装。
