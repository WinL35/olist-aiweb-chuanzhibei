### 2.2 但「接上」≠「接好」，必须同时改三处

| # | 问题 | 位置 | 不改的后果 |
|---|---|---|---|
| 1 | **Prompt 里没有出图指令**，输出结构锁死为【结论】【数据依据】【口径提醒】【局限】 | `llm/agent/prompts.py:24-28` | 模型永远只写字，不问不画 |
| 2 | **工具集 22 个全是查询型，没有一个能出图** | `llm/tools/registry.py` | 模型想画也没有手 |
| 3 | **接口没有 `history` 字段**，每次提问都是独立的一轮 | `app/llm_api.py:37` 的 `ChatIn` 只有 `question`/`mode` | 用户说「再按月份拆开看看」会完全失忆 —— 而多轮追问正是「对话式分析」的核心体验 |

### 2.3 关于「垂直」还是「通用」——必须提前想好怎么答

评委大概率会问：「你这是 Olist 专用的，怎么能叫数据分析平台？」

**不要改成通用平台**（10 天改不完，且会丢掉最值钱的算法资产）。正确答法是把它当卖点讲：

> 通用 BI 助手（Chat2SQL）在真实业务里最常翻车的是**口径**——「销售额」到底含不含运费、含不含取消订单、复购率的分母是谁。我们把这个领域的 33 条口径写成**代码级硬规则**，先于模型生效、模型无权绕过；再用 239 段领域文档做 RAG。所以它牺牲了「任意数据集即插即用」，换来的是**同一句问题在任何时候都得到同一个、可追溯的数字**。
>
> 这是「垂直深耕」而不是「能力不足」—— 通用 NL2SQL 的准确率瓶颈就在口径漂移，而口径是我们唯一不允许 AI 自由发挥的地方。

这套说辞有真实代码支撑（`hard_rules.py` 33 条 + `guard.py` 越界规则 13 条），比空喊「我们更专业」有力得多。

## 四、怎么改：把「可视化」这块补上

### 4.1 核心设计原则（这一条决定成败）

> **图表里的每个数字必须来自工具返回值；LLM 只被允许决定「画什么、怎么画」，不被允许提供「画多少」。**

为什么这么设计：如果让模型直接生成 ECharts 的 `series.data`，它一定会编数字 —— 一个编了数据的 BI 图，比没有图严重得多，且评委一眼能看出来（拿数字一核对就崩）。

技术实现：新增专用工具 `render_chart`，**参数里没有数据字段**，只有「用哪个工具的哪份结果」：

```python
# llm/tools/chart.py （新增）
def render_chart(chart_type: str, data_from: str, x_field: str,
                 y_fields: list[str], title: str = "", note: str = "") -> dict:
    """从「已经调用过的工具结果」里取数组装 ECharts option。

    chart_type : line | bar | pie | scatter | funnel
    data_from  : 工具名（如 dashboard_category）——后端从本轮上下文取它的返回
    """
    payload = executor.last_result(data_from)      # 关键：只认本轮的既成结果
    if payload is None:
        return {"ok": False, "error": f"{data_from} 本轮未被调用，不能凭空画图，请先调用它"}
    option = build_option(chart_type, payload, x_field, y_fields, title)  # 纯确定性转换
    return {"ok": True, "chart": option, "note": note}
```

对应的 system prompt 增补（改写 `prompts.py:24-28`）：

```
【回答结构】（markdown）
**【结论】** …
**数据依据** …
**可视化** 当用户问题涉及「对比 / 分布 / 趋势 / 占比 / 排行」，或明确要求画图时，
           必须先调查询工具拿到数据，再调 render_chart 出图。
           你不允许自己编造图表数据，图表数据只能来自查询工具的返回。
**口径提醒** …
**局限** …
```

### 4.2 前端改造（工作量主要在 `assistant.html`）

现在 `addMsg()` 只往气泡里塞 `render(text)` 生成的 HTML。要改成：

1. 后端响应新增 `charts: [option, ...]` 字段
2. `addMsg()` 在文字后面追加 `<div class="chart" data-idx="0"></div>`
3. 渲染后对每个容器 `echarts.init()` + `setOption(option)`
4. 每张图右上角加「导出 PNG」和「数据 CSV」两个按钮（`chart.getDataURL()` / 从 option 拼 CSV）

配套 CSS：气泡宽度要放宽（图放不下），并做响应式 `chart.resize()`。

### 4.3 为什么这一手能拿分

对比一下「普通选手」和「你」：

| | 普通做法 | 本方案 |
|---|---|---|
| 谁决定画什么 | 模型（或前端写死） | 模型决定，但受 Prompt 约束 |
| 图里的数字 | 模型生成（可能编） | **100% 来自 SQL/工具** |
| 口径 | 无 | 33 条硬规则 + 图注自动标注口径编号 |
| 做不出来的图 | — | 明确说「这个维度数据不支持」，并给替代方案 |

**「图注自动标注口径编号」** —— 例如品类 GMV 柱状图的右下角自动写「口径 R03：GMV 含运费、剔除 canceled」。这个细节几乎没有参赛作品会做，但对「数据分析专业度」的说服力极强，且实现成本很低（`citations` 机制已经有了）。
